# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**My Space** — a Tauri 2 desktop app intended to aggregate multiple internal/work tools behind a left sidebar, added one feature at a time. Scaffolded with **tauri-ui** (`bun create tauri-ui`, `vite` template + `--starter` dashboard). Stack: Tauri 2 (Rust) + React 19 + TypeScript + Vite + **Tailwind v4** + **shadcn/ui** (built on `@base-ui/react`, not Radix). Package manager is **bun**.

## tauri-ui reference

This project is based on the tauri-ui template. When working on template structure, shadcn/ui conventions, batteries (debug-panel, workflow), or scaffold options, consult the official docs: **https://tauriui.vercel.app/docs**

## Commands

Run from repo root. `bun` and `cargo` must be on PATH (`export PATH="$HOME/.bun/bin:$PATH"`; `source ~/.cargo/env` if `cargo` is missing).

```bash
bun install            # once
bun run tauri dev      # dev mode — opens the app window, hot-reloads (Ctrl+C to quit)
bun run tauri build    # production build → src-tauri/target/release/bundle/ (.dmg + .app)
./bin/install.sh       # 위를 감싼 배포용 래퍼 — PATH·서명키 준비 + .dmg 굽기 (--universal / --install / --help)
./bin/patch-version.sh # 릴리스 한 번 — 버전 올림 → 커밋·태그·푸시 → CI 감시 → 초안 퍼블리시 (--minor / --dry-run / --help)
bun run build          # frontend only: tsc -b + vite build (the type-safety gate)
bun run typecheck      # tsc --noEmit
bun run lint           # eslint
bun run format         # prettier --write
```

There is no test runner. `bun run build` (via `tsc -b`) is the type gate. First `cargo` compile is slow (~2 min, plus a few more for `rdkafka` — it builds bundled librdkafka from C source); later builds are incremental. Rust-only check: `cd src-tauri && cargo check`.

## Architecture

**Single window, Slack-style shell + menu-registry view switching (no router lib).** The UI mirrors the current Slack desktop app. `src/App.tsx` composes the shell from `src/components/shell/`, on a `bg-ui-chrome` root: `<TitleBar>` (40 px `bg-ui-chrome`, macOS Overlay title bar → 78 px left gap for the traffic lights, whole bar is `data-tauri-drag-region` except the centred pill, which is the **구성원 일정 빠른 검색** — `EmployeeSearchPalette` (`src/features/gcal/employee-search-palette.tsx`), a title-bar dropdown that searches the domain directory and shows one member's 이번주·다음주 일정 inline, reusing the gcal backend (`gcal_people` + `gcal_person_events`); it works even when the sidebar is collapsed. The old "My Space 검색" menu-filter — the pill, the ActivityBar "메뉴 검색" container, and the SideBar search input — was removed, so `ActivityContainerId` is now just `"explorer"`) → row of `<ActivityBar>` (64 px rail, icon above an 11 px label, theme toggle + 설정 at the bottom; re-clicking the active container collapses the sidebar) + `<SideBar>` (white panel, `rounded-tl-[var(--ui-panel-radius)]`, resizable via `myspace.sidebarWidth`) + editor area (`<TabBar>` = underline tabs + an 18 px bold view header, then the active view at `p-5`) → `<StatusBar>` (26 px, chrome-coloured). `src/main.tsx` wraps everything in `ThemeProviders` (preset + light/dark) and `ExternalLinkGuard`.

**Open views are tabs.** `src/lib/use-open-tabs.ts` owns `openIds` (localStorage `myspace.openTabs`) and `activeId` (`myspace.activeMenu`), and exports `SETTINGS_ID`. Closing the active tab activates the right neighbour, else the left; the last tab can't be closed. `move(draggedId, targetId, before)` reorders `openIds` (tab drag & drop). `src/components/shell/tab-bar.tsx` keeps tabs at a fixed width (`shrink-0`, 112–240 px, so names never get squeezed), scrolls the row when it overflows, and then shows an IntelliJ-style `⌄` list button (with the count of off-screen tabs) that opens every open tab in a dropdown.

**Tabs are keep-alive.** A tab's view mounts the first time it's activated and stays mounted until the tab is closed — going back to a tab must show the *previous* data, not re-fetch. Inactive tabs are stacked `absolute inset-0` and hidden with `invisible` (not `hidden`/`display:none`, which would reset their scroll position). Consequences to respect: (1) nothing may rely on unmount for cleanup on tab switch — use `useTabActive()` (`src/lib/use-tab-active.ts`, supplied by `TabActiveProvider` in `src/lib/tab-active-store.tsx`, `true` when there is no provider, e.g. the pet window) instead; (2) **periodic refresh must be gated on `useTabActive()`**, otherwise every open tab polls at once — `use-gcal.ts` / `use-jira.ts` show the shape: one effect does the initial load, a *separate* effect owns the `setInterval` and depends on `tabActive` (merging them would re-fetch on every tab switch, which is exactly what keep-alive avoids); (3) native child webviews are drawn *over* the window and ignore CSS, so **every view that embeds one** (`browser`, `cowork-ai`, `claude-design` — anything using `useWebviewBounds`) must call `browser_hide` when `tabActive` goes false and re-show via `browser_open` when it comes back, otherwise the embedded page stays on top of whatever tab you switch to.

**Browser memory: kill the `WebContent` process, never close the webview.** **One browser tab = one WKWebView = one `WebContent` process = 200–400MB**, so two tabs cost 600MB and hiding reclaims none of it. Everything that looks like it should free that memory was measured and **does not**: navigating to `about:blank`, `location.replace('about:blank')` (no bfcache entry left), and even releasing the WKWebView outright (`removeFromSuperview` + nil) all leave RSS at ~370MB with the process alive — WebKit holds `WebContent` in its process cache and that process never returns memory to the OS. The one thing that works is `kill_web_content()` in `lib.rs`: read the renderer's pid off the WKWebView with `_webProcessIdentifier` and `SIGKILL` it from a spawned thread. The process exits, returning every byte; WebKit immediately replaces it with an empty renderer (~56MB) and reloading the URL brings the tab back normally (measured: pid confirmed dead, replacement renderer 56MB). It is private API, so the pid is read behind a `respondsToSelector:` check — if a future macOS drops it, memory just stops being reclaimed and nothing breaks. **Killing the process is only half of it: without `with_process_terminate_hook()` Tauri puts the page straight back.** `tauri-runtime-wry` installs a default `on_web_content_process_terminate` handler whose whole body is `webview.reload()` (`tauri-runtime-wry-2.11.4/src/lib.rs:5133`), so every kill was measured being undone in the same second — `WebContent 프로세스 종료 pid=61772` followed by wry's `webview reloaded` and a fresh load of the tab's URL, RSS right back where it started. That is why `run()` starts with `with_process_terminate_hook(tauri::Builder::default())`: the app-level hook replaces the default (`prepare_webview` only fills in `pending.on_web_content_process_terminate_handler` when one is set, and wry skips its default branch when that field is `Some` — child webviews built by `add_child` go through the same path). It skips the reload for labels in `killed_labels()` and reloads everything else, so a genuine renderer crash still recovers exactly as before. `kill_web_content` must insert that label **before** sending `SIGKILL`, or the hook wins the race and revives the page. Measured after the fix: the daum.net tab's renderer (516MB) exited and *no* replacement renderer appeared at all. **Do not "fix" this back to `_killWebContentProcessAndResetState`. That selector does not work on macOS 26 (Darwin 25) and three ways of sending it were measured failing:** sent directly it returns with `respondsToSelector:` = `true` and the process stays alive (RSS unchanged, no wry "web content process terminated"); deferred with `performSelector:withObject:afterDelay:0` it is never even executed, because that API puts a timer on *the calling thread's* run loop and `kill_web_content` runs on a Tauri command thread that has no run loop; handed to the GCD main queue with `dispatch_async_f` the block does not run either. Reading a pid is a plain getter — no nested run loop, so none of the deadlock hazards that shaped the old code apply. `browser_close` still splits its work across ticks (hide now, kill, `close()` on a 1 s delayed thread) because webview teardown is asynchronous and the tab must leave the screen immediately. Closing the webview is a trap on top of all this: **wry 0.55 deliberately leaks it** — `impl Drop for InnerWebView` (`wkwebview/mod.rs:1396`) calls `removeFromSuperview()` then `self.webview.retain()`, putting the refcount back, so the object is never deallocated while Tauri's registry forgets it, and reopening the tab builds a *second* webview (wry 0.54.2 does the same; bumping the version does not fix it). So `browser_discard` hides the webview, kills its process, and records the label in `discarded_labels()`; `browser_open` sees the label there and re-navigates to the tab's stored URL, which is why the frontend never tracks what was discarded. `browser_close` exists only for the tab's own X button (that label is a tab id and never returns) and kills the process *before* closing, so the shell that wry leaks leaks empty. One more consequence: killing the process resets the webview to `about:blank`, so `on_page_load` must **not** emit `browser:navigated` for that URL — the frontend would overwrite the tab's stored address with `about:blank` and lose where it was (`use-browser.ts` also repairs tabs already poisoned that way).

Two supporting pieces. `browser_hide` sends `setHidden:YES` to the native WKWebView (`set_webview_hidden`, same `with_webview` + `msg_send!` route as the back/forward gestures) *and* keeps the old move-off-screen as the non-macOS fallback; a merely off-screen view is still on-screen as far as WebKit is concerned and keeps its backing store, GPU resources and full-speed timers. And `browser-view.tsx` empties tabs nobody has looked at for `settings.browser.discardMinutes` (설정 → 브라우저; default 5, 0 = never), dimming them in the tab strip. Four rules that timer keeps: it is the **one periodic job that must NOT be gated on `useTabActive()`** — being away from the browser is exactly when reclaiming matters; **"not looking" includes the window not being focused**, so the watched-tab decision is `visible && windowFocused` (`getCurrentWindow().onFocusChanged`) — `useTabActive()` alone only covers switching to another *menu* tab, and this is a tray-resident app whose browser tab sits active while you work in another app, which measured as the clock being rewound forever and the page never being reclaimed; that focus flag must stay **out of `visible`**, which decides whether the native webview is drawn — mixing it in makes the page vanish every time you click another app; the tab being watched has its clock rewound every tick via a ref, not an effect dependency (a dependency would reset the interval on every tab switch, so it would never fire); and closing the browser menu tab empties **every** tab immediately, since the tab list survives in localStorage and reopening only reloads the active one. A fifth rule falls out of killing the reload: **reviving a discarded tab is its own effect.** The tab that gets reclaimed most is the *active* one — browser menu tab open, you working in another app — and the only thing that changes when you come back is `windowFocused`, which the placement effect deliberately does not depend on, so nothing would reopen it and you'd return to a blank page (wry's auto-reload used to hide this). Adding `windowFocused` to the placement effect is the wrong fix: it also runs when focus is *lost*, calling `browser_open` on the tab that was just reclaimed and undoing the reclaim. So a separate effect opens the active tab only when it is both watched (`visible && windowFocused`) and actually dead (`!liveRef.current.has(activeId)`) — it no-ops otherwise, and the tab strip's "해제됨" dimming is cleared on the same condition so the indicator and the reality can't disagree.

**Any view can be popped out into its own window.** The view header's right-hand `↗` button calls the Rust command `open_view_window(id, title)`, which creates (or focuses) a window labelled `view-<menu id>` pointing at `index.html?view=<menu id>`; the tab stays open, so window and tab can sit side by side. `src/lib/window-role.ts` is the single source of truth for "which window am I" (`WINDOW_LABEL`, `isMainWindow`, `isViewWindow`, `viewWindowMenuId()`), `src/main.tsx` routes `view-*` to `ViewWindowRoot` (`src/features/popout/`), which wraps the same providers as `App.tsx` and renders one view — no tabs, so `useTabActive()` is always `true` and polling just works. `src/lib/view-info.tsx` (`viewInfo` / `viewElement`) maps an id → title/icon/group and element for the tab bar, `App.tsx`, and the pop-out window alike. Three things multi-window forces on you: (1) **global schedulers must be gated on `isMainWindow`** — `reminder-store.tsx` and `claude-activity-store.tsx` do, or a pop-out would fire every reminder twice and double-log activity; (2) `useLocalStorage` syncs across windows via the `storage` event (without it each window's stale snapshot would overwrite the other's writes); (3) native child webviews attach to the **calling** window (`browser_open` / `github_import_chrome_cookies` take `tauri::Window`) and their labels must come from `browserLabel()` so main and pop-out don't fight over one webview. New windows need their label glob in `src-tauri/capabilities/default.json` (`view-*`).

**Launch at login is on by default, and launches *silently*.** `settings.general.autoStart` (설정 → 일반, default **true** — the app is a tray resident whose whole point is watching for work, so off would make it pointless) is only the *intent*; the OS registration is `tauri-plugin-autostart` with `MacosLauncher::LaunchAgent` (a `~/Library/LaunchAgents` plist — the AppleScript launcher would prompt for "System Events" automation permission). `src/features/settings/use-autostart.ts` reconciles the two: `useAutoStartSync()` (mounted once in `App.tsx` as `AutoStartSync`, inside `SettingsProvider`) applies the setting on startup and on change, and the panel also awaits `applyAutoStart` so it can re-read and display the *real* registration state — registration can fail silently. Two things this forces: (1) **dev builds don't register** (`AUTOSTART_SUPPORTED` is false when `import.meta.env.DEV`), because the registered binary would be `src-tauri/target/debug/…` and cleaning the target dir would leave a broken login item behind; the panel says so instead of looking broken. (2) The plist launches the binary with `--autostart` (`AUTOSTART_FLAG` in `lib.rs`, which must stay in sync with the plugin's args), and `on_page_load` **skips `show()` for `main`** when `launched_at_login()` — so a login start puts the app in the menu bar with no window, while a manual launch behaves normally. The webview still loads (hidden), so herdr watching, notifications, and the pet all run; the tray's "My Space 열기" (`present_main`) brings the window out.

**Desktop pet (`pet` window)** — the character, and **the app's only notification surface**. There used to be a second window, `widget`, a popover anchored under the tray icon that showed reminders and Claude Code notices; the pet already showed the same things in its bubble, so the popover was deleted (one window fewer = one WebContent process fewer — see `src-tauri/src/pet.rs`'s header). 상시 표시 is off by default, toggled from 설정 → 데스크톱 펫 (`settings.pet`: `enabled` / `bubble` / `clickThrough` / `scale` / `notify`) or from the tray menu's 펫 표시/숨기기 (which can't flip localStorage from Rust, so `pet::request_toggle` emits `pet:toggle` and `PetController` does it). **Visibility is the OR of two axes**: `settings.pet.enabled`, and Rust's `pet:alert` — otherwise turning the pet off would silently swallow every reminder. `PetAlert` (`pet.rs`) holds that second axis **per source** (`AlertSource::Herdr` / `Reminder` / `App`); collapsing it to one bool means dismissing a reminder also clears the herdr alert, which the watcher loop then re-sets a tick later, and the pet blinks. Rust owns the signal rather than the pet because a hidden window's webview isn't loaded, so the pet can't notice it has something to say; it computes nothing about *size*, though — `PetController` (`src/features/pet/pet-controller.tsx`, mounted once in `App.tsx`, gated on `isMainWindow`) is what calls `pet_show` / `pet_hide`, because `petWindowSize()` / `readPetAnchor()` live there. `src/main.tsx` routes the `pet` label to `PetRoot` wrapped in `SettingsProvider` so the pet reads the same live settings. `src-tauri/src/pet.rs` owns the window: transparent, `alwaysOnTop`, `visibleOnAllWorkspaces`, `focus: false`. Three things it forces: (1) **the window is sized to its content, not the reverse** — transparent pixels still swallow clicks, so `PetRoot` measures itself with a `ResizeObserver` and calls `pet_resize`, which pins the **bottom centre** so a growing speech bubble doesn't shift the character. Two windows compute that size, which is where it goes wrong: `pet-metrics.ts` is the single source of truth (`PET_BASE`, `PET_PAD`, `petWindowSize()`), the controller passes `petWindowSize(scale)` — the **padded** size, not the character size — to `pet_show`, and `PetRoot` takes its padding from the same `PET_PAD` as inline style rather than Tailwind classes. Get that wrong and the first show clips the top of the character. Re-showing needs `pet_show`'s `pet:shown` event too: the content size hasn't changed, so the `ResizeObserver` stays silent and the window would keep whatever `pet_show` guessed; (2) for the same reason the saved position (`myspace.petAnchor`, `pet-anchor.ts`) is a bottom-centre anchor, not a top-left origin — the pet window writes it on `onMoved`, the controller reads it when showing; (3) the pet gets its state purely from the `herdr:*` / `reminder:*` events Rust already broadcasts with `app.emit` (`use-pet-mood.ts`), so it adds **no** polling of its own — and shows nothing new when 작업 감시 is off, because then no events are emitted. **`PetMood` is the behaviour spec, four states only** (`use-pet-mood.ts` is the source of truth; the settings panel's table mirrors it): `idle` = nothing running and nothing to confirm → *asleep* (closed eyes + a `Zzz` badge); `running` = one Claude task working; `busy` = two or more working (badge shows the count); `waiting` = something needs the user (task finished, AskUserQuestion, a fired reminder, or an app notice — new mail / Slack message / upcoming event). Priority is `waiting > busy > running > idle` — anything needing a human wins regardless of how many tasks are running. "Running" is counted per **herdr workspace**, not per herdr session, since one session can hold several tasks. Reminders are not a separate pose: they map to `waiting` and differ only in the badge, keyed off `PetNotice.kind` (never off the chip's text — that silently breaks when wording changes). The Petdex sheet has no sleeping row, so sprite species use its `idle` row and rely on the `Zzz` badge to say "asleep" — no species closes its eyes any more, so the badge is the only cue and the 설정 behaviour table is worded that way.

**Three interactions, three owners.** Dragging moves the window. Clicking the *character* toggles a **speed dial** — a column of menu icons that fans upward, each carrying an unread badge; picking one calls `pet_open_menu`, which shows the main window and emits `pet:open-menu`, and `App.tsx` turns that into `open(id)` (the tab state in `useOpenTabs` exists only in the main window, so the pet cannot open a tab itself). Clicking the *head badge* toggles a panel of **in-flight Claude tasks only** — `PetState.tasks`, whose `detail` is the **user's prompt**, since that is the answer to "what is it doing?". The two overlays are mutually exclusive: both stack above the character, and showing them together makes the window cover the screen. Running tasks never surface on their own — a bubble that stays up until a task finishes is just noise, so it is click-to-reveal. Keep unread counts out of that panel: they belong on the dial badges, and mixing two kinds of information into one list makes it unclear what you are looking at.

**Unread counts come from the main window, not from the pet.** `PetFeedPublisher` (mounted in `App.tsx`, gated on `isMainWindow`) reads the `SlackProvider`/`GmailProvider` state that is *already* polling and hands `{menuId, count}` records to Rust via `pet_set_feed`; Rust keeps them in `PetFeed` state and emits `pet:feed`, and the pet window subscribes plus queries `pet_feed` once on mount (`usePetFeedCounts`). **Do not "simplify" this back to localStorage + the `storage` event**: that path depends on window start order — if the pet webview loads before the first poll it reads an empty value and never sees the update, so the badges sit at 0 forever. The Rust-mediated path is the same one the herdr notices use, which is how the pet's mood already works. Mounting those providers in the pet window instead would double every poll and duplicate the connection state. Slack's count follows `slack-menu-badge` exactly, or the sidebar and the pet quote different numbers. **Gmail deliberately does not**: a dial icon has room for *one* badge, while `gmail-menu-badge` shows two (red = 관심, grey = all unread), so the dial takes the 관심 count only — falling back to all-unread would hang a three-digit number off the icon, which reads as noise rather than "look at this now". No 관심 filter configured (설정 → Gmail) ⇒ no Gmail dial badge. Dial icons and titles come from `MENUS` (`pet-dial-items.ts`) rather than being redeclared, so renaming a menu can't desync them.

**Which notifications the bubble carries is a setting, and it starts at Claude-only.** `settings.pet.notify` (설정 → 데스크톱 펫 → 받을 알림) has five sources: `claude` and `reminder` (생산성 → 알림 메뉴의 리마인더) default **on** — those two predate the setting, so the defaults *are* the old behaviour — while `gmail`, `slack`, and `gcal` default **off**, because a tray resident that announces every mail is noise. Google 캘린더 is the one source split into **parent + when**: `gcal` decides *whether* to notify, `gcalStart` / `gcalBefore` (both default on, but dead while the parent is off) decide *when* — the publisher gets `gcal && gcalStart` / `gcal && gcalBefore`. Two switches instead of three would mean turning the calendar off erases which timings you picked, so re-enabling costs two more clicks; the UI indents the two under the parent and dims them rather than hiding them (hidden controls read as "not supported"), and warns when the parent is on with neither timing chosen — that combination is silently inert. **Each source is muted at a different layer, and that is not an accident — it's where the notice is born.** `reminder` is cut off at the *scheduler*: `reminder-store.tsx` reads the setting and simply doesn't call `reminder_fire` (it still stamps `firedAt`/`lastFired`, so re-enabling doesn't dump every missed reminder at once, and it calls `reminder_dismiss` when you switch it off so an on-screen reminder doesn't outlive the setting and pin the pet open). Three paths, and the split is the whole point: **herdr notices are made by Rust**, so muting them frontend-only would leave the pet popping up over an empty bubble — `PetController` therefore pushes the flag down with `pet_set_claude_alert`, and `pet.rs`'s `AlertState` keeps `claude_muted` next to the per-source `active` array so `any()` ignores a muted source (and re-emits `pet:alert` the moment you toggle it, or the pet stays on screen looking un-muted). `usePetMood` *also* filters them, because a permanently-visible pet keeps receiving `herdr:*` events regardless of the alert axis. That filter cuts notice cards only — mood, `running`, and the task panel still animate while Claude works, since this is an "알림" switch, not a "stop watching" switch (that one is 작업 감시). **Gmail/Slack/캘린더 notices are made by the main window** and relayed through Rust exactly like the dial counts: `PetNotifyPublisher` (`pet-notify-publisher.tsx`, mounted in `App.tsx` inside the providers, gated on `isMainWindow`) calls `pet_notify`, Rust holds them in `AppNotices`, emits `pet:notices`, and the pet window subscribes + queries `pet_notices` once on mount (`useAppNotices` in `pet-notify.ts`) so a webview that cold-loads late still fills in. Three rules that publisher must keep or it turns into a spam machine: (1) **the first snapshot is seeded, not announced** — otherwise every already-unread mail fires the moment the app starts (and again whenever you re-enable the switch, which is why `useSeenIds` clears on `enabled: false`); (2) **ids are stable per source item** (`gmail:<id>`, `slack:<channel>:<ts>`, `gcal:before|start:<epoch>:<title>`) because polling hands back the same list every cycle; (3) **batches are capped** (`MAX_PER_BATCH` = 3) since the bubble only expands 2 cards anyway — don't cut it below the visible count, or the surplus vanishes without even reaching the "N개 더 보기" row. Gmail follows the badge's priority — 관심 filter if 설정 → Gmail has one, else all unread. The calendar arm is the one place with **its own poll** (`gcal_today` every 5 min + a 30 s due-check): `useGcal()`'s refresh is gated on `useTabActive()`, so events would go stale whenever the 캘린더 tab is closed — which is most of the time for a tray app. It skips all-day events (no start time to count back from) and only fires 정시 inside a 2-minute grace window, or launching the app in the evening would replay the whole day. TTL is owned by whoever *created* the notice: `notifyPet` schedules its own `pet_dismiss_notice` after `noticeSeconds` (0 = 항상 표시 keeps it until clicked), the same "frontend schedules, Rust relays" shape as `reminder.rs` — don't move a timer into Rust for this.

`usePetMood()` returns `{ mood, running, notices, tasks }`: the bubble stacks pending notifications (up to `MAX_VISIBLE` = 2, then an "N개 더 보기" row that opens the main window), because collapsing them all into one loses which task each is about while stacking them all makes the window — which is sized to its content — cover the screen and swallow clicks meant for the app behind it; `mood` comes from the first entry. Each row is built like a 작업목록 card — source icon (Claude logo for herdr, the service's brand logo for Gmail/Slack/캘린더, bell for reminders) + status chip + bold task name + muted prompt/recap — and the chip text/colour comes from `statusInfo()` in `agent-status.ts` so the pet and the task list never disagree. Task names come from the `herdr:workspaces` snapshot, **not** from `HerdrNotice`, whose `blocked` entries expire after 7 s while the wait itself lasts until answered. A notice may also carry `actions` — a button row under the card, which only reminders use (다시 알림 5분/30분/1시간 + 확인, the popover's controls moved verbatim). They are buttons rather than a card click because a single click can't distinguish 확인 from 5분 뒤 다시; the card click itself opens the 알림 menu. That row is a sibling of the card's body button, not nested inside it, and the card can't use `overflow-hidden` (it would clip the bubble tail), so the body carries matching `rounded-t`/`rounded-b` instead. Each card also carries an **X at its top right** (`dismiss`, another overlaid sibling — buttons can't nest — with `pr-7` on the body so the status chip doesn't slide under it), and what "dismiss" means differs per source, which is why it's a callback rather than one shared handler: a reminder does the real 확인 (`reminder_dismiss`, or the pet stays up on a live reminder), a 완료 알림 clears the Rust `Notices` entry too, but an **입력 대기 can't be cleared at all** — it lasts until answered in the terminal — so those are hidden locally by id. That hidden set is pruned **in the `herdr:questions` / `herdr:workspaces` listeners** (not in an effect — `react-hooks/set-state-in-effect` forbids it), using the same `questionId()` / `blockedId()` helpers that built them: skip the pruning and the same pane's *next* question reuses the id and never shows. Four things to know: (0) **only the frame size (192×208) and the column count (8) are fixed — the row count is not.** guga is 9 rows (1536×1872), boba is 11 (1536×2288); hardcoding 9 made each cell 254 px and rendered 1.3 characters per frame. `loadPetSprite` therefore derives `frameW = width/8`, `frameH = frameW * 208/192`, `rows = round(height/frameH)`, which also survives sheets drawn at 2× scale. (3) Sprite frames are 192×208, i.e. taller than wide, so `petdexAspect` is stored in settings and fed to `petWindowSize()`; `PetSpriteFigure` also deliberately skips `.pet-figure`, because the artwork already animates and stacking our CSS bob on top is nauseating.

**화면 공유 (`src/features/screen-share/` + `src-tauri/src/screenshare.rs`): the app is a *server*, not a capturer.** WKWebView does not support `getDisplayMedia()` — Apple only allows `getUserMedia` in the embeddable webview ([wry#1101](https://github.com/tauri-apps/wry/issues/1101)) — so the two options were (a) capture in Rust with ScreenCaptureKit and hand-roll H.264/VP8 + RTP, or (b) let the system browser capture and have the app only hand out URLs and relay signalling. This is (b): zero video-codec dependencies, and quality/latency are whatever Chrome's hardware encoder gives. `screenshare_start` opens `http://127.0.0.1:P1/s/<sender_token>` in Chrome (`open -a "Google Chrome"`, falling back to the default browser), the page calls `getDisplayMedia`, and the app's `Hub` relays SDP/ICE between that one sender and N viewers. Media never passes through the app. Five things this forces:
- **Two listeners, because of secure context.** `RTCPeerConnection` and `getDisplayMedia` only exist in a secure context. The sender is fine over plain HTTP because `http://127.0.0.1` is the localhost exception — no certificate warning. But a viewer opening `http://<LAN IP>` gets **no WebRTC at all**, so LAN viewers need HTTPS: `build_tls` mints a self-signed cert per session (`rcgen`, SAN = localhost + 127.0.0.1 + the LAN IP) for a second listener on `0.0.0.0:P2`. The viewer clicks through one warning; a tunnel avoids it. Don't "simplify" this to a single HTTP listener — the viewer page would load and then do nothing, which reads as a bug in the video path.
- **The HTTP listener is bound to 127.0.0.1 deliberately.** A warning-free plaintext origin must not be reachable from the network. cloudflared is pointed at *that* origin (`--url http://127.0.0.1:P1`) so there's no `--no-tls-verify` and the public TLS is terminated by Cloudflare.
- **There is no TURN server, so P2P is not enough — hence the relay fallback.** Signalling goes through the app, media is P2P, and on a different network STUN hole-punching often fails behind symmetric NAT or a corporate firewall. Rather than leave the viewer on a black screen, the viewer page falls back: on `connectionState` `failed`/`disconnected`, or after `P2P_TIMEOUT_MS` (8 s) without `connected`, it sends `{type:"relay",on:true}` and the sender tab starts pushing canvas→JPEG frames (5 fps, ≤1600 px, q=0.6) over the same WebSocket, which `Hub::broadcast_frame` fans out. So **anywhere the URL opens, the screen shows** — degraded, not broken. Three details: frames go *only* to the relay set (sending to a P2P viewer doubles upload for nothing); the sender drops frames when `bufferedAmount` exceeds 2 MB or a `toBlob` is still encoding, because a backed-up queue turns into snowballing latency; and `sender_socket` must send `relay-count` on attach as well as on change — a re-opened sender tab that only got `peers` would leave an existing relay viewer frozen. When P2P later reaches `connected`, the viewer sends `on:false` and returns to full quality.
- **Tunnels are cloudflared only. An SSH reverse tunnel (`localhost.run`) was tried and removed — don't bring it back.** It needed no install, and HTTP + WebSocket upgrade both verifiably passed through it, but a real share over it didn't work and it's a free shared service with no bandwidth or availability guarantee. A path that works sometimes is worse than no path: the failure surfaces as "the URL opens but the screen never appears", with nothing to point at. `rejects_the_removed_ssh_tunnel_domain` pins that `*.lhr.life` is no longer accepted. Consequence: without `cloudflared` there is **no** 사외 주소, so `screenshare_tunnel_available` is queried when the 뷰 mounts and the checkbox is disabled with a `brew install cloudflared` hint *before* starting — telling someone it failed after they've already sent an invite is too late. `extract_tunnel_url` still scans *every* `https://` on a line (cloudflared logs its docs URL too) and requires the `TUNNEL_DOMAIN` suffix. A public-IP URL (`https://<WAN IP>:port`) is not an option at all: this PC is behind corporate NAT, so it needs a firewall port-forward, which is IT's call.
- **`rustls` needs its CryptoProvider chosen explicitly.** Both ring and aws-lc-rs are in the dependency graph, so automatic selection panics; `ensure_crypto_provider()` installs ring once. `install_default` returns `Err` on every call after the first — treating that as a failure would make restarting a share impossible, which is why the test asserts `build_tls` twice.
- **A viewer URL must never contain loopback; the sender path must be localhost-only.** These are the same coin. `127.0.0.1` appears in exactly three places — the sender page URL, the tunnel's origin, and the cert SAN — and `viewer_urls_never_point_at_loopback` pins that the URLs handed to other people never do (a recipient opening one would see *their own* machine). Conversely `is_local_host` gates `/s/<token>` and `role=sender` on the `Host` header: the HTTP listener is bound to 127.0.0.1, but the tunnel uses it as its origin, so without that check a leaked `sender_token` lets someone outside attach as sender and replace what's on screen. The sender tab shows and copies those same URLs — it gets them over the socket as a `urls` message pushed from `emit_state`, not once at connect, because the tunnel URL only becomes available seconds later. Also `lan_ips()` returns **every** usable IPv4 (via `getifaddrs`, primary route first, loopback/link-local dropped) and the 뷰 lists them all — this machine is on wired `172.16.100.225` *and* Wi-Fi `192.168.11.94` at once, so publishing only the routed one locks out anyone on the other network. All of them go into the cert SAN too, or the second address adds a name-mismatch warning on top of the self-signed one.
- **Two tokens, not one.** The viewer link and the sender page carry *different* tokens, or anyone holding the viewing URL could attach as sender and replace what's on screen. `Hub` also keys the sender by an id: when a second sender tab attaches, the old one is told `replaced`, and `detach_sender` compares ids so the late-closing old socket doesn't tear down the new sender. Route patterns live in `build_router()` (state applied separately) because a bad axum pattern panics at `route()` — at share-start time, not compile time — so a test calls it.

**Claude Code watching has three backends — herdr, cmux and Orca, and only those three.** 세션 목록 (`src/features/claude-bridge/`) needs two things from the terminal side: (a) which pane is which **Claude `session_id`**, and (b) whether that session is working / blocked / done. herdr answers both over its socket CLI; cmux answers both through its event log; Orca answers both through its hook status file. A plain terminal emulator (Ghostty, iTerm2, Terminal) answers *neither* — Ghostty's AppleScript (1.3.0+) exposes `working directory` and can send input, but cannot read the screen and has no session mapping, so the list can't be filled. That's why `settings.claudeCode.backend` is a **list** (`ClaudeWatchTerminal[]`, persisted comma-joined) and the settings panel says only those three terminals are supported. **All three on is the default**, because any one alone shows part of the picture: herdr alone misses sessions started straight from the other two, and cmux alone **collapses herdr's workspaces into one tab** (they inherit the same `CMUX_WORKSPACE_ID`, so several tasks land in one card and 이동 only reaches the tab). Merging is safe because every backend carries the same Claude `session_id` — that's the dedup key. `dup_workspaces()` drops a *workspace* (not just the session) whenever any of its sessions is already known, i.e. "the tab where herdr is running": herdr's cards describe it better. Dropping per-workspace rather than per-session keeps the agent list and the workspace list cut on the same line, or a card would go empty or start representing someone else's status. Costing nothing when a backend is absent is what makes that default safe — no cmux means no event log to read, no Orca means the daemon-pid check fails before any process is spawned, no herdr means one failed CLI call. Everything above that boundary is backend-agnostic: the `herdr:*` event names, the `HerdrAgent` / `HerdrWorkspace` shapes, and — importantly — **all displayed data** (`last_prompt`, `recap`, `token_usage`, AskUserQuestion options) still comes from `read_session_info()` reading `~/.claude/projects/**/*.jsonl` plus the `~/.myspace/ask/<sid>.json` hook file. A backend supplies only the mapping and the status. Eight things this forces:
- **`src-tauri/src/herdr.rs` is the dispatcher**, not just the herdr client: `list_agents` / `list_workspaces` / `read_pane_text` and the four action commands check `backend()` and delegate to `crate::cmux::*` / `crate::orca::*`. With more than one on, **actions route by session name** (`route_of`) — cmux- and Orca-built entries always carry `session == cmux::SESSION` ("cmux") / `orca::SESSION` ("orca"), so a screen mixing terminals still sends each card's 이동·전송 to the right place; with exactly one backend on it routes there regardless of the name, so entries saved in an older format still work. A list call keeps whichever side succeeded (`unwrap_or_default` + warn), so turning all three on while using only one tool is fine. **The two list paths must iterate the non-herdr backends in the same order with the same `ws_of` rule** (`other_backends()` is that single list) or the agent list and the workspace list get cut on different lines. The watcher loop is untouched — it reads `backend()` every tick, so switching backends needs no restart. Rust can't read localStorage, so `ClaudeNotifier` pushes the choice via `herdr_set_backend` and Rust persists it to `~/.myspace/backend` (same trick as `watch-disabled`; the loop starts before any window exists). Empty persists as the literal `"none"`, because an empty file is indistinguishable from "never saved" and would resurrect the default. The legacy single-choice value `"both"` migrates to **all three** (it was the old default and meant "everything that existed then"), while a deliberate `"cmux"` stays narrow — `backend_from_str` and `migrateWatchBackend` must keep that rule identical or the panel and the watcher disagree about what is on.
- **cmux's data source is `~/.cmuxterm/events.jsonl`, not its socket.** The socket refuses us outright — "Access denied - only processes started inside cmux can connect" — and My Space launches from Finder/LaunchAgent. But `cmux-claude-wrapper` injects a hook bundle via `--settings` whenever `claude` runs inside cmux (nothing to install), and every hook lands in that log as `agent.hook.<Event>` carrying `session_id` (`"claude-<uuid>"` — **the uuid is the transcript filename**), `workspace_id`, `cwd`, `phase`, and `_ppid`. `scan_text()` replays the log oldest-first; `status_of()` is the whole status table (`Notification`/`PermissionRequest` → blocked, `Stop` → done, `SubagentStop` ignored for the same reason herdr's integration ignores it — it arrives after the turn already ended).
- **Actions still go through the CLI, so they need a password and the list doesn't.** `focus` / `send` / `read-screen` shell out to `/Applications/cmux.app/Contents/Resources/bin/cmux` with `CMUX_SOCKET_PASSWORD` from `settings.claudeCode.cmuxPassword` (cmux 설정 → Automation, key `automation.socketPassword`). Leaving it blank keeps the list, status, and notifications fully working and breaks only those three — say that wherever the field appears, or it reads as a required value. An `Access denied` sets a 60 s backoff (`DENIED_UNTIL`) because the watcher tries a screen read per pane every 800 ms; `set_socket_password` clears it so a freshly typed password isn't ignored for a minute.
- **`pane_id` must stay `"<workspace>:<pane>"`.** `claude-bridge-view.tsx`'s `paneOf` finds a workspace's pane with `pane_id.startsWith(workspace_id + ":")`, so cmux emits `"<ws uuid>:<surface uuid>"` (`pane_ref`) and `parse_target` splits it back into `--surface`/`--workspace`. Deriving the flag from a fresh snapshot instead would re-parse a 1 MB log per pane per tick.
- **Two staleness guards.** Only the newest `boot_id` is replayed (a restarted cmux dropped every old workspace), and an agent whose `_ppid` is no longer in `ps` is filtered out — a `kill -9`'d Claude never sends `SessionEnd`. If cmux itself isn't running the snapshot is empty rather than showing last session's state.
- **Orca joins two sources on `"<tabId>:<leafId>"`.** Orca (`src-tauri/src/orca.rs`, [onorca.dev](https://www.onorca.dev/docs)) is an agent IDE, not a multiplexer, and it splits the two answers: `~/Library/Application Support/orca/agent-hooks/last-status.json` holds per-pane `providerSession.id` (= the Claude transcript filename), `payload.state` and `payload.agentType`, written tmp+rename on every hook; `orca terminal list --json` holds the live `handle`, `title` and `worktreePath`. The status file's entry key **is** `tabId:leafId`, which `terminal list` hands over as two fields — that's the join. Orca installs its hooks globally in `~/.claude/settings.json`, but `claude-hook.sh` exits immediately without `ORCA_PANE_KEY`, so Claude runs outside Orca never appear. State names map straight across (`working`→working, `waiting`→blocked, `done`→done); that table was read out of Orca's own bundle, not guessed — **don't "simplify" `waiting` away**, it is the entire 입력 대기 path.
- **Orca needs the CLI for the list too, so it is cached and pre-gated.** The status file keeps entries for **7 days** after a pane closes (Orca's `HYDRATE_MAX_AGE_MS`), so the file alone lists last week's work; `terminal list` is the liveness filter (and supplies the action handle) the way cmux uses `_ppid`. But `bin/orca` is a shell wrapper that boots Electron as node — ~140 ms a call, and the watcher lists twice every 800 ms. Hence `TERMS_TTL_MS` (2 s) caching of the roster only — the status file is re-read every time, so working/waiting/done transitions are never delayed — plus `runtime_alive()`, which reads `orca-runtime.json` (the socket/token/pid file Orca writes on start and deletes on exit) and `kill(pid, 0)`s it so a closed Orca spawns nothing at all. **Gating on the daemon pid instead is wrong and was the bug**: `daemon/daemon-v*.pid` outlives the app — the daemon keeps running as `Orca Helper` after you quit Orca, and old version-suffixed pid files stay behind — so with Orca closed the gate passed and the watcher spawned a doomed CLI every time the 2 s cache expired, filling the log with `Could not read Orca runtime metadata … Start the Orca app first.` `orca-runtime.json` is the file the CLI actually needs, so its presence *is* the gate. Failures that slip past it (no CLI, permissions) are logged only when the message changes (`note_fail`), for the same reason. A pane with no status entry is a plain shell, not an agent, and is dropped.
- **Orca's workspace is one pane, and `pane_id` puts the handle last.** A card per pane, not per worktree — grouping by worktree would recreate exactly the cmux problem of several agents collapsing into one card that 이동 can't reach individually. So `workspace_id` is the pane key and `pane_id` is `"<tabId>:<leafId>:<handle>"`: that keeps `paneOf`'s `startsWith(workspace_id + ":")` rule while `rsplit_once(':')` recovers the handle. Handles are **runtime-scoped** (Orca restart invalidates them), which is why they are never stored and `focus_workspace` re-looks-them-up. Unlike cmux there is no password: `terminal switch|send|read` need nothing but a running Orca.

Only 10 px `APP`/`WORKFLOW`-style tags may be uppercase.
- Slack is **generous with bold**: titles, people's names, buttons, and the active tab are `font-bold`. Emphasis comes from weight *and* colour.
- Density: sidebar nav rows are `h-(--ui-row-h)` = 28 px as `mx-1.5 px-2 rounded-lg` pills; content rows are `min-h-9` (36 px) `px-3 py-1.5 rounded-lg`; panels use `p-4` (headers `px-4 py-3`), the editor area `p-5`. Separate rows with spacing, not borders.
- Radius is `rounded-lg` (8 px, `--radius: 0.5rem`), `rounded-[10px]` for panels/cards, `rounded-full` for badges, chips, reactions, filter buttons, and date dividers. Avatars are `rounded-lg` rounded squares, not circles. `rounded-none` survives only on full-height panels (sheet/drawer) and joined segments.
- Shadows are back: `shadow-[0_1px_3px_rgba(0,0,0,0.06)]` on cards/panels, `shadow-[0_4px_16px_rgba(0,0,0,0.16)]` on floating overlays, nothing elsewhere. Focus is a 2 px ring: `focus-visible:outline-2 focus-visible:outline-offset-1 focus-visible:outline-solid focus-visible:outline-ring` (`outline-solid` is required — Tailwind v4's base `outline-none` otherwise suppresses it).
- Status colours come from `ui-error` (`#E01E5A`) / `ui-warning` / `ui-success` / `ui-info` — Slack's brand four — never hardcoded palette classes (`text-amber-500`, …). Links are `text-ui-link`; mentions are `bg-ui-mention text-ui-mention-fg` chips, group/keyword highlights `bg-ui-highlight`.
- **Two independent theme axes.** *Presets* (`src/lib/themes.ts`): `slack` (default), `vscode`, `claude`, `intellij`, `discord`, `raycast` — six, in that order — set every colour. *Slack themes* (`src/lib/slack-themes.ts`, key `myspace.slackTheme`, 34 entries in Slack's own four groups) override **only** `--ui-chrome` / `--ui-chrome-fg`, i.e. the title bar, rail, and status bar; `null` means "use the preset's chrome". Their `<style>` must stay *after* the preset's in `<head>` — `:root` and `.dark` have equal specificity, so order decides. `from`/`to` draw the sphere swatch only; `chrome` is the flat colour actually applied, and `chromeFg` was pre-picked as white or `#1D1C1D` by contrast. Presets change **colour only**; structure, density, and type scale above stay fixed. Each supplies a saturated brand chrome (light mode: Slack `#862688`, VS Code `#117BC1`, IntelliJ `#365EB2`, Claude `#C05731`, Discord `#6069E4`, Raycast `#C84E4B`; dark mode one step deeper) with `chromeFg: "#FFFFFF"`, and a brighter tone of the same hue as `selection`. Chrome values are tuned so white text keeps a 4.5:1–8:1 contrast ratio — re-tune, don't eyeball, if you change them. `--ui-badge` and `--ui-list-active-fg` follow `--ui-selection`/`--ui-selection-fg`.
- `src/features/pet/*` (the desktop-pet character) is exempt from all of the above.

## Releasing & auto-update

Distribution target is **macOS Apple Silicon only** (no OS code signing/notarization yet — recipients bypass Gatekeeper on first launch). Auto-update is wired via `tauri-plugin-updater` + GitHub Releases.

**How it works:** `App.tsx` calls `checkForUpdates()` (`src/lib/updater.ts`) once on startup. It reads `latest.json` from the endpoint in `tauri.conf.json` → `plugins.updater.endpoints` (`.../releases/latest/download/latest.json`), compares versions against `tauri.conf.json` `version`, and if newer prompts via a sonner toast → downloads → `relaunch()`. Updater artifacts are signed with a minisign key; the **public** key lives in `tauri.conf.json` `plugins.updater.pubkey`.

**Releasing is one command: `./bin/patch-version.sh`** (`--minor` / `--major` / `--set x.y.z`, `--dry-run` to see the plan). Commit your work first, then run it. It bumps the version, commits, tags, pushes, watches the Actions run, publishes the draft, and then **verifies `latest.json` actually serves the new version** — that last check is the only proof users can update. Flags exist to stop partway (`--no-wait`, `--no-publish`, `--skip-check`) or to widen what the release commit picks up (`--include-dirty`, `--include-untracked`).

What it automates, and why each step is load-bearing:
1. The version lives in **four** files — `src-tauri/tauri.conf.json` (the one the updater compares), `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock` (the `my-space` package block — stale here and cargo rewrites it mid-build, dirtying the tree), and `package.json`. The build succeeds when they disagree, so hand-editing goes wrong silently. The script writes all four and re-reads them to confirm.
2. `release.yml` triggers on **`v*` tags only** — pushing a commit to `main` does nothing.
3. `.github/workflows/release.yml` builds `macos-latest` aarch64 via `tauri-action`, signs, and creates a **draft** release with the `.dmg`, `.app.tar.gz`, `.sig`, and `latest.json`.
4. **The draft must be published** (`gh release edit <tag> --draft=false --latest`) — `releases/latest/download/` does not serve drafts. Skipping this is invisible: the endpoint 404s and the app's startup check fails *silently* (`checkForUpdates(silent = true)` shows nothing). This is exactly what happened to `v0.0.1` — CI succeeded and uploaded all four assets to a draft that was never published, so the endpoint has 404'd since.
5. **Untracked new files break CI and nothing local catches it.** A new source file left untracked is absent from the release commit, so the *committed* code that imports it fails to compile — but only on the runner: locally the file exists, so `bun run typecheck` and the script's own pre-check both pass. `v0.0.3` died this way (7× `TS2307` for `features/auth/*`, `cowork-spec/bundled-css`, `gcal/employee-search-palette`). The script therefore **stops** on untracked files rather than warning; `--include-untracked` folds them into the release commit. Related: when you delete a failed tag and re-push it, the old failed Actions run has the *same* `headBranch`, so the run must be matched by `headSha` — matching on tag name alone reports the new build as failed the instant it starts.
6. **`gh` acts as its own logged-in account, which on this machine has only `pull` on the repo** (`gh api repos/rudaks-han/my-space --jq .permissions` → `push: false`), while `git push` uses a different credential from the helper. So pushes and tags work but releases 403, and the draft — created before the tag exists, hence named `untagged-…` — doesn't even appear in `gh release list`. It looks like CI never made a release. `bin/patch-version.sh` falls back to the credential-helper token (`git credential fill` → `GH_TOKEN`) for the publish step; the alternative is publishing from the web UI.

Draft-then-publish is kept deliberately over `releaseDraft: false`: assets upload to the draft and go public in one step, so there's no window where `latest.json` announces a version whose `.app.tar.gz` hasn't finished uploading.

Two things to know about how updates reach users: the updater installs the **`.app.tar.gz`**, not the `.dmg` (the app replaces its own bundle and relaunches — no re-install, no `xattr` dance; that's first-install only), and the check runs **only at app startup**, so a tray-resident app that nobody restarts won't notice a release. Also, CI builds **aarch64 only** — `latest.json` has no `darwin-x86_64` entry, so Intel users never update.

**Required GitHub secrets** (Settings → Secrets and variables → Actions): `TAURI_SIGNING_PRIVATE_KEY` (contents of `~/.tauri/myspace-updater.key`) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (empty for the current key). ⚠️ The private key is **not** in the repo — losing it breaks the update chain for installed apps.

**Two things break a *local* `bun run tauri build` on this machine, and `bin/install.sh` exists to absorb both.** (1) `createUpdaterArtifacts: true` + a `pubkey` in `tauri.conf.json` means the build **fails at the very end** — after the `.app` is already bundled — with "A public key has been found, but no private key"; `bin/install.sh` exports `TAURI_SIGNING_PRIVATE_KEY` from `~/.tauri/myspace-updater.key` (and `…_PASSWORD=""`, or tauri stops to prompt), falling back to `--config '{"bundle":{"createUpdaterArtifacts":false}}'` when the key is absent. (2) `.dmg` bundling mounts a temp volume at `/Volumes` and copies the app in, and **that write is EPERM on this machine** — not a TCC problem: Ghostty *has* Full Disk Access (`com.mitchellh.ghostty|2` in the system TCC.db) and the same image mounted under `$HOME` is writable, so the block is `/Volumes`-path-based, done by the corporate EndpointSecurity agent (`com.jiran.endprotection` — OfficeKeeper — plus FortiClient; see `systemextensionsctl list`). **No terminal permission fixes that**, so don't send anyone to System Settings again. `bin/install.sh` probes with a 1-second throwaway image and, when blocked, builds `--bundles app` and bakes the `.dmg` itself with `hdiutil makehybrid` + `convert` — that path never mounts anything, and exec bits, symlinks, the `/Applications` drag target, and the adhoc signature all survive (verified). What's lost is only the Finder window dressing (background image, icon positions), which `bundle_dmg.sh` needs a writable mount to set. `hdiutil create -srcfolder` is **not** an alternative — it mounts and copies too, and fails the same way.
